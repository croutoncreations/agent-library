# Ranked search

Home → **Search library** searches current published heads across the owner's projects. Existing project list search is unchanged. Agents get the read-only `search_artifacts` tool on both MCP implementations. Publishers do not get general search. No external search service, embeddings, model call or new binding is used.

## Contract and examples

```json
{"query":"annual subscriptions","project_ids":["planning","notes"],"limit":20}
```

Call `search_artifacts` with this object. Omit `project_ids` for all currently readable projects; `[]` means no projects. The optional filters are `kind`, `updated_after`, `updated_before`, `limit` and `cursor`. Kind is one of markdown/html/json/csv/binary; timestamps are ISO datetimes, exclusive bounds. Limits: query 200 UTF-16 code units, 1–16 distinct words, 20 explicit project IDs, default page 20 and maximum 50. Unknown fields and malformed filters return `invalid_input` (400).

HTTP: `GET /api/search?query=annual%20subscriptions` (owner session), or `GET /v1/search?query=annual%20subscriptions&project_ids=planning,notes&limit=20` (API-key bearer). The machine endpoint follows the existing `/v1` API-key authentication convention. OAuth read scopes are enforced by the MCP host; legacy grants use their existing project scope. No grants or client registrations are changed by searching.

Response:

```json
{"results":[{"project_id":"planning","project_title":"Planning","artifact_id":"art_example","title":"Annual subscriptions","kind":"markdown","matched_field":"title","snippet":"Renew annually in January.","indexed_body":true,"revision":3,"sha256":"<revision hash>","updated_at":"2026-10-27T12:00:00.000Z","web_url":"https://library.example.com/p/planning/a/art_example?v=3","preview_url":"https://library.example.com/p/planning/a/art_example/preview?v=3"}],"has_more":false,"next_cursor":null}
```

Each excerpt is plain source text, at most 500 characters; HTML source is displayed as text, never executed. Binary matches use titles only and `indexed_body:false`. JSON/CSV follow the existing App Connect feature flag; OAuth connections approved without file access cannot search binaries. Title-only matches still show a short body excerpt or their title. Excerpts are built from the first 16,384 characters of the indexed text: when the matching words occur only later in the document, the excerpt is the start of the text (or the title when that prefix holds no complete word). When a better group of matching words lies beyond those characters, the excerpt is the best one within them. A query word that the index splits into several words (for example Hebrew or Arabic written with vowel points) is found by the index as a phrase but is not located by the excerpt, which then shows the start of the text. Ranking and which documents are returned are unaffected. UI highlighting uses text nodes; it is decorative and may differ from FTS accent folding.

## Lexical semantics and ranking

NFC-normalize, trim and collapse whitespace. Extract Unicode letter/number/mark runs, deduplicate them and join individually quoted FTS5 tokens with AND. All words must occur somewhere in the title or body. Case and accents fold under D1's `unicode61 remove_diacritics 2`; punctuation and quotation marks separate words. There are no phrase, prefix, boolean or SQL operators: `a OR b` searches for all three words. Punctuation-only queries are rejected. No stemming or question interpretation is attempted. Unicode scripts follow unicode61 word boundaries (for example, contiguous CJK text is one token).

Score is 1000 for an exact full title using SQLite `lower()`, plus one for each query word appearing in the lowered title. SQLite's title score folds ASCII case; FTS matching supports wider Unicode case/accent folding. Ties use updated time descending, then artifact ID ascending. No BM25 or corpus statistics: inaccessible files cannot influence ordering, snippets, pagination or counts. `has_more` reflects an additional *authorized* row (or results deferred by the response budget); there is no total-count endpoint.

Pagination is live, not a snapshot. Opaque HMAC-signed cursors expire after 15 minutes. They encode only a query/filter/identity binding hash, expiry and the last score/time/ID, never bodies or permission decisions. A random installation-local signing key is generated once in D1 by the migration and never returned over the API. Pagination performs no KV reads or writes, so it cannot consume the KV write quota used by OAuth. The query, filter and limit must remain the same; malformed, expired or mismatched cursors return `invalid_cursor` (400). Every page rechecks current grants and ownership inside candidate selection. Scope removal applies immediately; an explicit inaccessible project gets the same 404 as a nonexistent project. Static corpora have no duplicate/missing rows. Edits between pages can move documents across the boundary, causing omissions or repeats; restart for a fresh traversal.

The service budgets the full 64 KiB JSON-RPC envelope, including the duplicated text/structured result and request ID. If necessary it shortens the page and resumes after the last returned hit. MCP IDs above 1024 encoded bytes are rejected without echoing them. HTTP results share this conservative page budget.

## Required infrastructure / rollout

1. Apply **0031_search_contentless.sql** in a manual owner window ([destructive migrations](deploy-pipeline.md#destructive-migrations): it drops the derived index and its triggers, so it carries an `owner-approved-destructive` marker and the pipeline never auto-applies it). It recreates `artifact_search` as a **contentless** FTS5 table (`content='', contentless_delete=1`), adds `revision_id`, `sha256` and `indexed_title` to `artifact_search_keys` and sets the readiness flag to zero when documents exist. Nothing else is derived from the dropped table. The Worker needs SQLite 3.43+ for `contentless_delete`; the pinned local Wrangler/workerd runs SQLite 3.53.4 and is what the tests exercise.
2. Deploy the new Worker. Until the index is rebuilt, Home hides the search entry, both MCP catalogs omit the tool, and direct HTTP searches return `503 search_initializing`. The owner-only `/api/search/status` reports the activation flag `ready` without counts or content; an activated installation can still return `search_initializing` on an actual search if a later index gap is found.
3. **The rebuild is the Worker's cron** (every 15 minutes, `rebuildSearchIndex` in `packages/core/src/search/indexing.js`); there is nothing to run by hand. Each run re-indexes up to 15 documents that the completeness probe (`artifact_search_missing`) reports missing or stale, reading their text from R2 (or the legacy inline `revisions.body`), and sets `ready=1` once none is. It is safe to repeat and to run concurrently, and it also repairs gaps left by an interrupted write. A document whose R2 object is missing is indexed by its title only and logged. Allow about one cron run per 15 documents (300 documents: five hours); a deliberate wait is not needed on a new installation, which starts ready and empty.
4. After any database restore/import into a *different* D1, the cron rebuilds the same way. Search uses explicit `INTEGER PRIMARY KEY` identities from `artifact_search_keys` and joins by artifact ID; VACUUM or changes to the implicit `artifacts.rowid` do not break result identity.

## What the index stores

`artifact_search` is a contentless FTS5 table: D1 keeps the inverted index (words, positions) and **no copy of any title or body**. Text lives only in R2 (`revisions.body_key`, or inline `revisions.body` for legacy rows). Measured with the same 10 KB documents, the index is about 38% of the size of the previous stored-copy index (`node scripts/search/measure-index-size.mjs 2000`: 38.0 MiB before, 14.6 MiB after; `test/search-index-size.test.mjs` asserts it stays below 60%).

Because the table cannot be read back or edited in place, **every change to a current head, a title or a trash state writes the index in the same D1 batch as the change** through one module, `packages/core/src/search/indexing.js`: `indexDocument(db, {artifactId, revisionId, sha256, text})` returns prepared statements (delete the document's old entries, insert the new ones, record the indexed revision, hash and title in `artifact_search_keys`), `unindexDocument(db, artifactId)` removes a trashed document and `unindexMany` clears a purged project. They take a D1 handle, so the index can move to its own database later. There are no triggers. Callers: create, save, publish, restore revision, template copies, text-upload finish, App Files PUT/DELETE, backup restore and import, trash/untrash and title changes (`updateMetadata`), and the project purge. A binary file is indexed by its title only. At most the first 1 MiB (1,048,576 UTF-8 bytes) of a document is indexed; that cap no longer saves storage, it bounds the CPU and the size of one statement. Words only after it are not searchable.

Search joins the key row's revision, hash and title against the current head, so an entry that fell behind is never returned, and `artifact_search_missing` reports it until the cron repairs it (searches answer 503 meanwhile, never a confident empty result). Writers that bypass the module (raw SQL, an older Worker that still relied on the removed triggers) therefore cause a visible, self-healing gap rather than wrong results. Rolling the Worker back after 0031 is not supported: the previous Worker expects the stored-copy table and its triggers.

**Excerpts** are read after the page of at most 50 results is chosen: the first 16,384 characters of each result's current text, from inline `revisions.body` (SQL `substr`) or one ranged R2 read per R2-backed result (`getTextPrefix` in `content-store.js`, a few at a time), then the unchanged `rsExcerpt`. A missing R2 object shows the title.

Cloudflare's [supported SQL extensions](https://developers.cloudflare.com/d1/sql-api/sql-statements/#supported-sqlite-extensions) document FTS5; the pinned real local Wrangler/workerd tests exercise these statements. Production capability/latency was not probed. **Operational caveat:** Cloudflare [documents limitations for D1 exports involving virtual tables](https://developers.cloudflare.com/d1/best-practices/import-export-data/). Operators using whole-database SQL exports must review that workflow before rollout; project backups and D1 Time Travel remain separate mechanisms. The [deployment recovery runbook](deploy-pipeline.md#destructive-migrations) uses a verified Time Travel bookmark instead of whole-database SQL export. No resource IDs, domains, cloud credentials, DNS, Access policy, cron or binding changes are required. The signing key is internal derived-feature state in D1, not a new Worker secret.

## Verification

`node --test test/ranked-search.test.mjs` uses local D1, real HTTP, the official legacy MCP SDK client, the OAuth/publisher harness and Chrome. It covers ranking, buried matches, static pagination, query-bound cursors, grant scope changes, lifecycle and the cron rebuild, a contentless-table check, words beyond the excerpt prefix, index follow-up on replace/rename/trash/delete, App Files PUT/DELETE, concurrent versions, Unicode/operators, safe browser highlights, keyboard/filter behavior, loading/empty/error views and complete wire budgets. Screenshots and a reproducible six-project/300-document performance sample are written to `tmp/proof-of-work/ranked-search/`; `benchmark.json` reports corpus size, body/response bytes, elapsed request time and SQL query count. The unfiltered first-page search service executes two SQL SELECTs (readiness/key and candidates); explicit project filters add one authorization SELECT. Authentication and MCP tool-catalog activation checks are additional transport work. MCP catalogs and direct search tool calls read only the singleton activation flag; they never run the corpus completeness scan. Initialize, ping and unrelated tool calls make no search-state query. A failed activation query hides search while preserving the existing tool catalog. Actual searches still perform the full metadata completeness probe. Home and `/api/search/status` read only the singleton activation flag. Cursor signing uses WebCrypto without KV operations. Readiness checks inspect metadata and indexed head identities, not full bodies, but their cost grows with corpus size. These are local measurements, not production targets.

PDF extraction, OCR, video transcription, semantic search, guest sharing and finer-than-project permissions are outside this feature.

Concurrent checkouts can run checks in a separate port bank: `AGENT_LIBRARY_TEST_PORT_OFFSET=3000 npm test` (integer 0–5000). Every harness listener still takes its port from `test/ports.mjs`; choose a free bank.

KV quota note: the previous design wrote one opaque cursor per page to the shared OAuth KV namespace. This implementation uses stateless signatures instead; search pagination consumes none of those writes. Cloudflare’s [KV limits](https://developers.cloudflare.com/kv/platform/limits/) list 1,000 writes per day on the Free plan, shared with other application use.

Read-cost tradeoff: every actual search and each cursor page checks current-head completeness across the entire installation. That scans artifact/revision/key metadata with FTS rowid lookups, so D1 rows read scale with the corpus size times the number of search pages. This intentionally preserves truthful results after index gaps or old-Worker writes; it does not scan document bodies. The Free plan’s 5 million daily D1 rows-read allowance is shared with the rest of the application. Home renders, status checks and tool catalogs use only the singleton flag and do not perform this scan. See [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).

Excerpt cost: each page of results adds up to 50 ranged R2 reads (one per R2-backed result, at most 64 KiB each, six at a time). The excerpts are computed in the Worker, not in D1 (FTS5 `snippet()` takes time proportional to the square of the matches in one document and held the database for minutes on a large document). For a page of 50 results that are each longer than 16,384 characters, the excerpts measured 22–90 ms of CPU in local Node; this has not been measured on a deployed Worker. Smaller pages cost proportionally less and short documents far less. Workers Paid allows this. Workers Free allows 10 ms of CPU per request, so there a search whose results are long documents can fail with Cloudflare error 1102; a smaller `limit` lowers the cost. See [Workers limits](https://developers.cloudflare.com/workers/platform/limits/#cpu-time).

Tokenizer tables: `packages/core/src/search/unicode61.js` reproduces the index's tokenizer (`unicode61 remove_diacritics 2`) from tables read out of SQLite 3.53.4, and `test/search-excerpt-differential.test.mjs` checks them for every code point against `node:sqlite`. They have not been compared with D1's SQLite build. A difference would change only where an excerpt is centred, never which documents are returned.
